# 0007: Continuous integration, generated-types check, dependency updates

Status: Done
Owner code: `.github/workflows/ci.yml`, `.github/dependabot.yml`, `scripts/db-types.mjs`,
`scripts/slowest-tests.mjs`, `scripts/ci-changes.mjs`, `package.json`, and for AC-8 `.github/pull_request_template.md`, `.claude/hooks/stop-check.mjs`, `CLAUDE.md`, `specs/README.md`

## Goal

The regression gate does not depend on Claude Code: every pull request update, and every merge into `main`, runs the
same checks on GitHub, once per change, plus the end-to-end tests (except for a pull request that changes only Markdown). The committed database types never drift from the migrations, and dependency updates
arrive as small, tested pull requests.

## Behaviour

- **AC-1**: On every pull request update and every push to `main` (AC-9), a `check` job ("Typecheck, lint, unit tests") on `ubuntu-latest` with
  Node 24 runs `npm ci` and `npm run check` (typecheck, lint, unit tests). npm's cache is reused between runs.
- **AC-2**: An `e2e` job ("End-to-end tests"; it waits for the `check` job and is skipped for a Markdown-only pull
  request, AC-10) starts the local Supabase with the Supabase CLI (the version
  pinned in `package-lock.json`), installs Playwright's Chromium, runs the database rule tests (specs 0024, 0002, 0006, 0004 and 0035: `tests/friends-migration.test.ts`,
  `tests/database-rules.test.ts`, `tests/seed-cleanup.test.ts`, `tests/feature-flags-database.test.ts`, `tests/flag-admin-database.test.ts`) and `npm run e2e`. The Playwright HTML report is uploaded as an artifact when the job fails. Its caches, JSON
  report and slowest-tests summary are AC-6 and AC-7.
- **AC-3**: `npm run types:gen` writes `src/lib/supabase/database.types.ts` from the **local** test
  database, which is built from `supabase/migrations`, the source of truth. `npm run types:check`
  regenerates into memory and fails with a short diff hint when the committed file differs. The `e2e`
  job runs `types:check` after `supabase start`. The file keeps a header comment saying it's
  generated and how to regenerate it.
- **AC-4**: Dependabot opens weekly pull requests for npm (minor and patch updates grouped into one PR,
  majors separately) and for GitHub Actions. CI runs on them like on any PR. Major updates of `typescript`
  and `eslint` are ignored for now (see Notes), and so are those of `@types/node`, which must follow
  the Node version we run, not the newest one.
- **AC-5**: Nothing in CI needs a secret: the E2E job only talks to the local Supabase, and the unit
  tests never touch the network.
- **AC-6**: The `e2e` job restores two caches before it needs them: Playwright's browser download
  (`~/.cache/ms-playwright`, keyed by the locked `@playwright/test` version) and Next's incremental build cache
  (`.next-e2e/cache`, keyed by `package-lock.json` and the source files, with a fallback to the newest cache of the
  lockfile). The Next cache folder also holds the server's cached reference data (spec 0002 AC-15), which would
  hide a changed seed or migration, so the job deletes `.next-e2e/cache/fetch-cache` after restoring. A cache miss
  only makes the job slower, never fails it.
- **AC-7**: The job reports the slowest tests: Playwright's `list` reporter is joined by `json` in CI
  (`PLAYWRIGHT_JSON_OUTPUT_NAME`), and a final step prints the ten slowest tests to the job summary. It runs even
  when the suite failed.

### Once per change, and only what the change needs

- **AC-9**: A change is tested once. The workflow is triggered by `pull_request` (every update of a pull request: GitHub
  tests the result of merging it into `main`) and by `push` only on `main`; a push to a topic branch with an open pull
  request starts one run, not two. Every merge into `main` runs CI there: that run catches a bad
  merge and is the one the deploy workflow waits for (spec 0026 AC-1). A topic branch without a pull request, and a pull
  request with a merge conflict (GitHub starts no run for it), is not tested by CI: `npm run check` and the Stop hook run
  the same checks locally. A `concurrency` group per pull request cancels the earlier run when a new push arrives; a run
  on `main` is grouped by its commit and never cancelled, so every merge commit is tested. The job names ("Typecheck, lint,
  unit tests", "End-to-end tests") never change: `CLAUDE.md` and spec 0026 refer to them. Draft pull requests run CI like
  any other.
- **AC-10**: A pull request whose changed files are all Markdown (`*.md`, anywhere in the tree; a file renamed from or to
  another extension counts under both names) does not run the `e2e` job: the first step of the `check` job runs
  `scripts/ci-changes.mjs` on the merge commit that GitHub checks out (a checkout of depth 2) and publishes
  `code_changed`; `e2e` needs `check` and runs only when `code_changed` is `true`, which also stops it when `check` fails.
  Any other file in the diff, a list that cannot be read, or an empty one runs everything. A push (to `main`) always runs
  both jobs, so the deploy workflow never sees a skipped one. The `check` job always runs: it holds the tests that guard
  the Markdown files (`tests/specs.test.ts`, `tests/review-process.test.ts`). No job is added for the detection: it is a step of the `check` job. A skipped "End-to-end tests" check counts as a pass for the merge step of `CLAUDE.md`:
  green means passed, or skipped on a Markdown-only pull request. "Review recorded" is not affected.
- **AC-11**: Removed. A job "Up to date with main" used to flag a pull request whose base branch had moved on, because GitHub's "require branches to be
  up to date" setting was not available for a private repository on the free plan. The ruleset on `main` (spec 0021) enforces it now, so the job is gone.

### Who runs the end-to-end tests

- **AC-8**: CI is the authority for the end-to-end tests: the pull request checklist, `CLAUDE.md`, `specs/README.md`
  and the Stop hook say that the "End-to-end tests" job must be green on the pull request (skipped for a Markdown-only one,
  AC-10), and that a local `npm run e2e` is
  only for reproducing a failure.

## Out of scope

Deployments (spec 0026), the backup workflow (spec 0012), and the setting of the ruleset on `main` itself (a repository setting; spec 0021 describes it).

## Notes

- Why once per change: a change that is tested twice only duplicates the result, and the end-to-end job (about 5 to 6
  minutes) runs only when it can tell something. The price of the
  order: `e2e` starts after `check` (about a minute later), in return for not starting when the cheap job fails. The
  three checks the ruleset on `main` requires (spec 0021) are "Typecheck, lint, unit tests", "End-to-end tests" and
  "Review recorded"; a skipped job (end-to-end on a Markdown-only pull request, "Review recorded" on Dependabot's) counts as a pass.
- CI tests the merge of the pull request into `main` as it was when the run started, so two pull requests that are each green
  could break `main` together; the ruleset's "require branches to be up to date" setting (spec 0021) is what stops that: a branch
  that is behind cannot be merged until `main` is merged into it and CI has run again.
- The workflow also holds the pull-request-only job "Review recorded", which is not a regression check: spec 0022 AC-5 owns it.
- `scripts/db-types.mjs` runs `npx supabase gen types typescript --local --schema public` (only `public`: without
  the flag the local CLI also emits the `graphql_public` schema). It prepends the header comment and normalises
  line endings, so the check is stable across Windows and Linux. The CLI's output is unformatted and has no
  `__InternalSupabase` marker (the cloud API adds it; postgrest-js only uses it for `maxAffected` and
  spread-on-many typing, which the app doesn't use): local is the source.
- The `e2e` job starts Supabase with `-x studio,mailpit,imgproxy,vector,logflare,supavisor,edge-runtime,realtime,storage-api`
  (`config.toml` already disables realtime, storage, edge runtime and analytics): the stack comes up with database,
  Kong, auth, PostgREST and postgres-meta, which is all the app and `supabase status -o json` (read by
  `scripts/test-env.mjs`) need. `postgres-meta` is not excluded: the stack was only verified with it running.
- Dependabot ignores major updates of `typescript` and `eslint`. On TypeScript 7 `tsc` passes but typescript-eslint
  refuses it (its supported range is below 6.1). On ESLint 10, `eslint-plugin-react` (inside `eslint-config-next`)
  calls `context.getFilename`, removed in ESLint 10; wrapping the plugins in `@eslint/compat`'s `fixupPluginRules`
  makes ESLint 10 pass, so it is possible later, while TypeScript 7 would need two TypeScript versions side by side
  and Next's build also reads the `typescript` package. Neither gives us anything we use. Delete the `ignore`
  entries in `.github/dependabot.yml` when `typescript-eslint` supports TypeScript 7 and `eslint-config-next` ships
  a plugin set that runs on ESLint 10.
- Actions are pinned to major tags; Dependabot keeps them current.
- The suite runs on the single worker Playwright picks on the 2-core runner: more workers were slower (162 s against
  143 s for the test phase, single tests 2 to 4 times slower), because Next, Postgres and Chromium already use both
  cores. Faster needs less work per test, more cores (a larger runner) or splitting across jobs (issue #66, "0031: Sharded end-to-end tests", not built).
- Typical times: the `check` job about 1 minute, the `e2e` job 4 to 5 minutes (Supabase start about 60 s, `npm ci`
  15 to 20 s, browser install about 17 s with the cache, build about 13 s with a cache hit, tests about 2 minutes).
