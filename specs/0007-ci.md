# 0007: Continuous integration, generated-types check, dependency updates

Status: Done
Owner code: `.github/workflows/ci.yml`, `.github/dependabot.yml`, `scripts/db-types.mjs`, `package.json`

## Goal

The regression gate must not depend on Claude Code: every push and pull request runs the same
checks on GitHub. The committed database types must never drift from the migrations, and dependency
updates arrive as small, tested pull requests.

## Behaviour

- **AC-1**: On every push and pull request, a `check` job on `ubuntu-latest` with Node 24 runs `npm ci`
  and `npm run check` (typecheck, lint, unit tests). npm's cache is reused between runs.
- **AC-2**: An `e2e` job starts the local Supabase with the Supabase CLI (the version pinned in
  `package.json`), installs Playwright's Chromium, and runs `npm run e2e`. The Playwright HTML report
  is uploaded as an artifact when the job fails. Its caches, JSON report and slowest-tests summary are spec 0030 AC-3, AC-4.
- **AC-3**: `npm run types:gen` writes `src/lib/supabase/database.types.ts` from the **local** test
  database, which is built from `supabase/migrations`, the source of truth. `npm run types:check`
  regenerates into memory and fails with a short diff hint when the committed file differs. The `e2e`
  job runs `types:check` after `supabase start`. The file keeps a header comment saying it's
  generated and how to regenerate it.
- **AC-4**: Dependabot opens weekly pull requests for npm (minor and patch updates grouped into one PR,
  majors separately) and for GitHub Actions. CI runs on them like on any PR. Major updates of `typescript`
  and `eslint` are ignored for now (see Notes), and so are those of `@types/node`, which must follow
  the Node version we run, not the newest one.
- **AC-5**: Nothing in CI needs a secret: the E2E job only talks to the local Supabase, and the unit
  tests never touch the network.

## Out of scope

Deployments, branch protection rules (repo settings, done by the user), and the backup workflow
(spec 0012).

## Notes

- The workflows take effect once they are pushed to GitHub. They were
  validated locally as far as possible: all three YAML files parse (js-yaml), `npm run check` and
  `npm run types:check` pass, and the `e2e` job's Supabase step was rehearsed on a second, throwaway
  local stack (below). What can't be checked until the first push: that the actions run on GitHub's
  runners at all (action versions, Docker image pulls, Playwright's browser install, runtime).
- `scripts/db-types.mjs` runs `npx supabase gen types typescript --local --schema public` (only
  `public`: without the flag the local CLI also emits the `graphql_public` schema). It prepends the
  header comment and normalises line endings, so the check is stable across Windows and Linux.
- The committed file was regenerated from the local database once. The diff against the cloud-generated
  version is cosmetic only: the CLI's output is unformatted (different indentation, quoting and line
  breaks; it suggests `oxfmt`, not a dependency here), and the `__InternalSupabase: { PostgrestVersion }`
  marker is gone (the cloud API adds it; postgrest-js only uses it for `maxAffected` and
  spread-on-many typing, which the app doesn't use). `Tables` (every Row/Insert/Update/Relationships)
  and the helper types are identical modulo formatting. Local is the source from now on.
- The `e2e` job starts Supabase with `-x studio,mailpit,imgproxy,vector,logflare,supavisor,edge-runtime,realtime,storage-api`
  (`config.toml` already disables realtime, storage, edge runtime and analytics). That exact command
  was run on a second stack (other `project_id` and ports, so the real test stack stayed untouched):
  it comes up with database, Kong, auth, PostgREST and postgres-meta; `supabase status -o json`
  (read by `scripts/test-env.mjs`) works with the excluded services stopped; the dummy login's
  sign-up and sign-in succeed and PostgREST serves the seeded checkpoints; and `gen types` on that
  fresh database is identical to the committed file. The full `npm run e2e` was not run against it.
  `postgres-meta` is not excluded: the stack was only verified with it running.
- CLAUDE.md's migration workflow says `npm run types:gen` instead of the MCP tool.
- First run on GitHub (2026-10-02, commit `2236397`): both jobs green (`check` 55 s, `e2e` 3 m 41 s).
  Dependabot's first two pull requests (TypeScript 5.9 to 7.0, ESLint 9 to 10) failed, and not because of
  our code. On TypeScript 7.0.2 `tsc` passes, but `eslint` stops: typescript-eslint refuses TypeScript 7
  (its supported range is below 6.1; support for 7.1 and later is tracked upstream). On ESLint 10.11 it
  stops in `eslint-plugin-react` 7.37.5 (calls `context.getFilename`, removed in ESLint 10; its newest
  release only declares ESLint 9). Wrapping the plugins in `@eslint/compat`'s `fixupPluginRules` makes
  ESLint 10 pass with findings identical to ESLint 9 on a file of deliberate violations, so ESLint 10 is
  possible later; TypeScript 7 would need two TypeScript versions side by side, and Next's build also
  reads the `typescript` package. Neither gives us anything we use, so `.github/dependabot.yml` ignores
  major updates of these two packages; delete the `ignore` entries when `typescript-eslint` supports
  TypeScript 7 and `eslint-config-next` ships a plugin set that runs on ESLint 10.
- Actions are pinned to major tags (`checkout`, `setup-node`, `upload-artifact` at `v7`, the latest
  when this was written); Dependabot keeps them current.
