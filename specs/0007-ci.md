# 0007: Continuous integration, generated-types check, dependency updates

Status: Accepted
Owner code: `.github/workflows/ci.yml`, `.github/dependabot.yml`, `scripts/db-types.mjs`, `package.json`

## Goal

The regression gate must not depend on Claude Code: every push and pull request runs the same
checks on GitHub. The committed database types must never drift from the migrations, and dependency
updates arrive as small, tested pull requests.

## Behaviour

- **AC-1**: On every push and pull request, a `check` job on `ubuntu-latest` with Node 24 runs `npm ci`
  and `npm run check` (typecheck, lint, unit tests). npm's cache is reused between runs.
- **AC-2**: An `e2e` job starts the local Supabase with the Supabase CLI (the version pinned in
  `package.json`), installs Playwright's Chromium, and runs `npm run e2e`. The Playwright HTML report
  is uploaded as an artifact when the job fails.
- **AC-3**: `npm run types:gen` writes `src/lib/supabase/database.types.ts` from the **local** test
  database, which is built from `supabase/migrations`, the source of truth. `npm run types:check`
  regenerates into memory and fails with a short diff hint when the committed file differs. The `e2e`
  job runs `types:check` after `supabase start`. The file keeps a header comment saying it's
  generated and how to regenerate it.
- **AC-4**: Dependabot opens weekly pull requests for npm (minor and patch updates grouped into one PR,
  majors separately) and for GitHub Actions. CI runs on them like on any PR.
- **AC-5**: Nothing in CI needs a secret: the E2E job only talks to the local Supabase, and the unit
  tests never touch the network.

## Out of scope

Deployments, branch protection rules (repo settings, done by the user), and the backup workflow
(spec 0012).

## Notes

- The repo has no GitHub remote yet; the workflows take effect once the user pushes. Validate them
  locally as far as possible: YAML parses, every `run:` command works on this machine, and
  `types:check` passes against the running local test database.
- The local stack's generated types may differ cosmetically from the cloud project's output (e.g. the
  `PostgrestVersion` value). Regenerate the committed file from local once, check that the diff is
  cosmetic, and keep local as the source from now on.
- After this spec, CLAUDE.md's migration workflow says `npm run types:gen` instead of the MCP tool.
