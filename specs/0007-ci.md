# 0007: Continuous integration, generated-types check, dependency updates

Status: Done
Owner code: `.github/workflows/ci.yml`, `.github/dependabot.yml`, `scripts/db-types.mjs`,
`scripts/slowest-tests.mjs`, `package.json`

## Goal

The regression gate does not depend on Claude Code: every push and pull request runs the same checks on GitHub,
plus the end-to-end tests. The committed database types never drift from the migrations, and dependency updates
arrive as small, tested pull requests.

## Behaviour

- **AC-1**: On every push and pull request, a `check` job ("Typecheck, lint, unit tests") on `ubuntu-latest` with
  Node 24 runs `npm ci` and `npm run check` (typecheck, lint, unit tests). npm's cache is reused between runs.
- **AC-2**: An `e2e` job ("End-to-end tests") starts the local Supabase with the Supabase CLI (the version
  pinned in `package-lock.json`), installs Playwright's Chromium, runs the database rule tests (specs 0024, 0002, 0006 and 0004: `tests/friends-migration.test.ts`,
  `tests/database-rules.test.ts`, `tests/seed-cleanup.test.ts`) and `npm run e2e`. The Playwright HTML report is uploaded as an artifact when the job fails. Its caches, JSON
  report and slowest-tests summary are AC-6 and AC-7.
- **AC-3**: `npm run types:gen` writes `src/lib/supabase/database.types.ts` from the **local** test
  database, which is built from `supabase/migrations`, the source of truth. `npm run types:check`
  regenerates into memory and fails with a short diff hint when the committed file differs. The `e2e`
  job runs `types:check` after `supabase start`. The file keeps a header comment saying it's
  generated and how to regenerate it.
- **AC-4**: Dependabot opens weekly pull requests for npm (minor and patch updates grouped into one PR,
  majors separately) and for GitHub Actions. CI runs on them like on any PR. Major updates of `typescript`
  and `eslint` are ignored for now (see Notes), and so are those of `@types/node`, which must follow
  the Node version we run, not the newest one.
- **AC-5**: Nothing in CI needs a secret: the E2E job only talks to the local Supabase, and the unit
  tests never touch the network.
- **AC-6**: The `e2e` job restores two caches before it needs them: Playwright's browser download
  (`~/.cache/ms-playwright`, keyed by the locked `@playwright/test` version) and Next's incremental build cache
  (`.next-e2e/cache`, keyed by `package-lock.json` and the source files, with a fallback to the newest cache of the
  lockfile). The Next cache folder also holds the server's cached reference data (spec 0002 AC-15), which would
  hide a changed seed or migration, so the job deletes `.next-e2e/cache/fetch-cache` after restoring. A cache miss
  only makes the job slower, never fails it.
- **AC-7**: The job reports the slowest tests: Playwright's `list` reporter is joined by `json` in CI
  (`PLAYWRIGHT_JSON_OUTPUT_NAME`), and a final step prints the ten slowest tests to the job summary. It runs even
  when the suite failed.

## Out of scope

Deployments (spec 0026), branch protection rules (repo settings, done by the user; spec 0021 says why they are
off), and the backup workflow (spec 0012).

## Notes

- `scripts/db-types.mjs` runs `npx supabase gen types typescript --local --schema public` (only `public`: without
  the flag the local CLI also emits the `graphql_public` schema). It prepends the header comment and normalises
  line endings, so the check is stable across Windows and Linux. The CLI's output is unformatted and has no
  `__InternalSupabase` marker (the cloud API adds it; postgrest-js only uses it for `maxAffected` and
  spread-on-many typing, which the app doesn't use): local is the source.
- The `e2e` job starts Supabase with `-x studio,mailpit,imgproxy,vector,logflare,supavisor,edge-runtime,realtime,storage-api`
  (`config.toml` already disables realtime, storage, edge runtime and analytics): the stack comes up with database,
  Kong, auth, PostgREST and postgres-meta, which is all the app and `supabase status -o json` (read by
  `scripts/test-env.mjs`) need. `postgres-meta` is not excluded: the stack was only verified with it running.
- Dependabot ignores major updates of `typescript` and `eslint`. On TypeScript 7 `tsc` passes but typescript-eslint
  refuses it (its supported range is below 6.1). On ESLint 10, `eslint-plugin-react` (inside `eslint-config-next`)
  calls `context.getFilename`, removed in ESLint 10; wrapping the plugins in `@eslint/compat`'s `fixupPluginRules`
  makes ESLint 10 pass, so it is possible later, while TypeScript 7 would need two TypeScript versions side by side
  and Next's build also reads the `typescript` package. Neither gives us anything we use. Delete the `ignore`
  entries in `.github/dependabot.yml` when `typescript-eslint` supports TypeScript 7 and `eslint-config-next` ships
  a plugin set that runs on ESLint 10.
- Actions are pinned to major tags; Dependabot keeps them current.
- The suite runs on the single worker Playwright picks on the 2-core runner: more workers were slower (162 s against
  143 s for the test phase, single tests 2 to 4 times slower), because Next, Postgres and Chromium already use both
  cores. Faster needs less work per test, more cores (a larger runner) or splitting across jobs (spec 0031, a draft).
- Typical times: the `check` job about 1 minute, the `e2e` job 4 to 5 minutes (Supabase start about 60 s, `npm ci`
  15 to 20 s, browser install about 17 s with the cache, build about 13 s with a cache hit, tests about 2 minutes).
