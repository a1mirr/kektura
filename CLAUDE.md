# Kektura tracker

Tracks progress on the Országos Kéktúra (Hungary's Blue Trail): Google sign-in, mark the 161 official stamping places (plus extra stamps), see walked km, stages, a map and a route planner.

Stack: Next.js 16 (App Router, TS, Tailwind 4), next-intl (`hu` default, `en`, `de`, `ru`), Supabase (Google OAuth, Postgres + RLS), MapLibre, Recharts, Vitest + Testing Library, Playwright. Next 16 differs from older versions (`src/proxy.ts` instead of middleware, `params` are Promises): read `node_modules/next/dist/docs/` before using an unfamiliar API.

## Commands
- `npm run dev` (port 3000, production Supabase via `.env.local`); `npm run build`
- `npm test` / `npm run test:watch`; `npm run check` = typecheck + lint + tests (the Stop hook's gate)
- Test server: `npm run testdb:start` | `testdb:reset` | `testdb:stop` (local Supabase in Docker), `npm run dev:test` (port 3001, dummy login)
- `npm run e2e`: Playwright against a production build of the test server on port 3002

## Workflow
A change goes through these steps in order. CI (`.github/workflows/ci.yml`) runs the same checks plus E2E once per change, on every pull request update and on every push to `main`, never twice for a branch with a pull request, and a pull request that changes only Markdown skips the E2E job (spec 0007 AC-9, AC-10); on pull requests it also runs the "Review recorded" job (step 7); its "Security checks" job (`npm audit` and gitleaks, spec 0007 AC-14 to AC-16) also runs weekly, and a failure of it, on a pull request or on `main`, stops the merge or the deploy: fix it or allow-list it with a reason and an expiry; `backup.yml` dumps user data weekly; `deploy.yml` deploys after a merge (spec 0026).

1. **Task first** (spec 0034). Behaviour lives in `specs/product/` and `specs/project/`: one contract per area, written as it behaves *now* (test: will the sentence still be true in a year? then it is a spec). Work lives in GitHub issues labelled `task` (never in the repository): one issue per piece of work, closed once done, never a description of behaviour. A feature or behaviour change starts as a task, an issue opened with `gh issue create` from the template `.github/ISSUE_TEMPLATE/task.md`: the specs it touches, its requirements as a checklist of outcomes (`R-n`, no numbered acceptance criteria) and its open questions, which are settled with the user before coding (in the issue). The issue number is the task's number. No spec is drafted beforehand: a spec describes only behaviour that is built (its status is always `Done`), so the owning spec is edited while the behaviour is built (a new area: `specs/_template.md`, into `specs/product/` or `specs/project/`). A refactor, CI or deploy change, rename, data update or schema-only change is a task and changes no spec (unless it changes a rule a spec states); a trivial fix needs neither. Spec numbers are their own sequence (next = the highest in `specs/` + 1); tasks are numbered by GitHub (`#N`), and the tasks that predate the issues are closed issues whose titles keep their old number (`0054: …`). Specs and tasks are always written in English. Tests cite specs, never tasks: `describe("spec NNNN: …")`, `it("AC-n: …")`. Changing behaviour = edit the owning spec (never renumber ACs) + its tests in the same change as the code. Details: `specs/README.md`, `.github/ISSUE_TEMPLATE/task.md`.
2. **Build, then make the specs true.** Turn the task's requirements into numbered acceptance criteria of the owning spec and tests that cite them as you build. Logic in `src/lib` as pure functions with unit tests; pages only fetch and render. Components get `*.test.tsx` with `// @vitest-environment jsdom`. Async Server Components can't be unit-tested: cover them with E2E. Behaviour no test can reach (a real Google sign-in, native browser UI, WebGL pixels, a real deploy) gets a `manual` coverage row with its reason, how to check it and when it was last checked, written only by whoever did the check (spec 0034 AC-11); where a test would do, write the test. The **Stop hook** (`.claude/hooks/stop-check.mjs`) blocks the end of a turn until typecheck + lint + unit tests are green, and asks once when app code changed without a spec change, or a file users can see changed without a changelog entry (spec 0034 AC-10, AC-12): fix the failure, don't work around it. CI's "End-to-end tests" job is the authority for the end-to-end tests (spec 0007 AC-8): it has to be green on the pull request (skipped is fine for one that changes only Markdown, spec 0007 AC-10); run `npm run e2e` locally only to reproduce a failure (it needs Docker, so the hook doesn't run it either). When the build is done, and before the review, reread every spec the task touches against the code *as built* and edit it until it mirrors reality: an AC for behaviour that exists and no AC states, `Removed` for one that was dropped, status, coverage table, the index in `specs/README.md`; check off every requirement of the task or strike it with the reason; where code and spec disagree, decide which is right and fix that one. Write what changed in the pull request description's "Spec changes" section; the task issue closes with the merge (`Closes #N` in the description). A spec that is not true is a defect: fix one you find disagreeing with the code on the spot, or open a task.
3. **Migrations go local first.** New file in `supabase/migrations`, named `NNNN_slug.sql` after the number of the task issue that adds it, padded to four digits (`0075_x.sql` for #75; a migrated task whose title still starts with its old number, `0048: …` = #75, takes the issue number, not the old one; `0024_friends.sql` carries its spec's number and the older 0001-0008 predate this). The CLI takes the digits as the version, which must be unique, so a task owns one migration file: edit it until it is applied to production, then a later schema change needs its own task. It must not depend on a higher-numbered migration (production applies in merge order, a fresh reset by number) → `npm run testdb:reset` → tests + E2E. RLS policies use `(select auth.uid())` and `to authenticated`.
4. **Changelog** (spec 0018 AC-7). A change users can see (behaviour, a rename, a page) adds or extends an entry in `src/content/changelog.ts` in the same pull request, in every language; process, test, refactor and deploy-file changes add none. Dates can't repeat, so a change made on the newest entry's date joins that entry. A feature flag is no excuse while it is on in production (look it up: a flagged page answers 404 while the flag is off, e.g. `curl -s -o /dev/null -w "%{http_code}" https://kektura-tracker.com/en/friends` says 307 when on; never assume it); a change behind a flag that is off needs no entry until the pull request that switches the flag on. The Stop hook asks about the changelog for committed work too, not only for the working tree.
5. **Branch and pull request.** `main` is GitHub's default branch and the one that gets deployed. Work on a topic branch in a worktree of your own (below), push it and open the pull request yourself with `gh pr create --base main --head <topic> --title "<title>" --body-file <file>`. `gh` is installed machine-wide (`C:\Program Files\GitHub CLI`, on the system PATH, signed in as `a1mirr`; a terminal opened before the install needs a restart). A shell without a terminal can't answer gh's prompts, so title and body are always given; start the body file from a copy of `.github/pull_request_template.md` (gh doesn't apply it to `--body-file`) and fill in its checklist and review findings. Look at CI with `gh pr checks <n>` once, never with `--watch` or a sleep loop: a wait blocks everything else. If the run is still going, do other work and look once more later (the same goes for a deploy run). Spec 0021 owns these pull request rules and the hook. Never push to `main` on GitHub: a `pre-push` hook (`.githooks/`, spec 0021) refuses it. Install it once per clone with `npm run hooks:install`; pushing to the `production` remote is unaffected. Always work in your own worktree, never in the primary checkout and never on `main` (spec 0021 AC-7: the `worktree-guard` hook refuses file edits and mutating git commands there): `git fetch origin` as a call of its own, then `git worktree add .claude/worktrees/<name> -b <topic> origin/main` (new work starts from the real `origin/main`, never a local `main`, which can be days behind: the hook refuses any other base, or an `origin/main` that is not what GitHub has; spec 0021 AC-9; junction `node_modules`: `cmd /c mklink /J node_modules <primary>\node_modules`); leave other sessions' uncommitted files alone.
6. **Fresh-context review before merge** (spec 0022). When the change is done and committed (specs made true, `npm run check` green; CI's end-to-end job is looked at before the merge, step 7) and before it is merged, an agent with no context of the work reviews it: spawn the `fresh-reviewer` agent (`.claude/agents/fresh-reviewer.md`) and tell it only the task's issue number (`#N`; the spec number for a change that is only a spec, `none` for a small change that has neither) and the base branch (`origin/main`, after `git fetch origin`: a local `main` can be stale), never your reasoning or what to look at. Fix every valid finding and answer the rest in the pull request description, with the commit that was reviewed. Fixes that change code, tests or behaviour get another fresh review (a review of an earlier state doesn't count); wording-only fixes don't, so the pull request's head is the reviewed commit plus, at most, wording fixes. Never hand a pull request over as ready to merge without it, and leave the working tree alone while the review runs. Every change a person or Claude writes is reviewed, documentation included; Dependabot's pull requests are not (CI judges them). In the session that edited the agent file, spawn a general-purpose agent with the file's body as the brief (agents load at session start).
7. **Merge, migrate, deploy.** Merge with `gh pr merge <n> --merge --match-head-commit <full-sha>` (the repo uses merge commits; the full 40-character sha of the pull request's current head, `git rev-parse HEAD` after the last push: the reviewed commit plus, at most, wording fixes; a draft needs `gh pr ready`) on the owner's standing permission (given in chat on 2026-10-03, revocable) for pull requests you wrote, once CI is green and the fresh-context review is done (CI's jobs: "Typecheck, lint, unit tests", "End-to-end tests" and, for a pull request that is not Dependabot's, "Review recorded": it fails unless the description's `Reviewed commit:` line names the head or an ancestor with only Markdown changed after it, spec 0022 AC-5 (files that arrive by merging `main` into the branch don't count); it reads the description fresh, so after editing it re-run just that job with `gh run rerun <run-id> --job <job-id>`; a pull request that changes only Markdown skips "End-to-end tests", and a skipped job counts as green: spec 0007 AC-10; a red "Security checks" job blocks the merge like any other, spec 0007 AC-14 to AC-16, and `gh run rerun` applies to it too) and the branch is up to date with `main`, which the ruleset "Protect main" (`.github/rulesets/protect-main.json`, spec 0021 AC-11) enforces: GitHub refuses the merge of a branch that is behind (another pull request was merged meanwhile, and two green pull requests can break `main` together), so merge `origin/main` into the branch (`git fetch origin` as a call of its own), run `npm run check`, push and wait for CI again, with no new review for what arrives from `main` (spec 0021 AC-6); never `--admin`. Delete the pull request's branch after the merge, remote and local: `git fetch origin`, check it is in `main` (`git merge-base --is-ancestor origin/<topic> origin/main`), retarget any open pull request that is based on it (`gh pr edit <m> --base main`), `git push origin --delete <topic>`, then `git branch -d <topic>` from a checkout whose HEAD contains the merge (in your own worktree: `git switch --detach origin/main` first; never `-D`). Delete only branches of pull requests you merged, or that the user asked you to clean up: if another session has the branch checked out, leave the local branch and tell the user. Afterwards remove what the merge left behind: `npm run tidy` shows what it would remove, `npm run tidy -- --apply` does it (worktrees under `.claude/worktrees` and local branches that a merge commit brought into `origin/main`, never one with unmerged or uncommitted work or a new branch with no commit yet; it also moves a stale local `main` up; spec 0021 AC-8, AC-9). It keeps the worktree it runs in, so yours goes with the next run from another checkout; run it from a checkout that has the script (a worktree on a recent `origin/main`). The merge itself deploys (spec 0026, `.github/workflows/deploy.yml`): once CI is green on `main` it applies the missing migrations to production, pushes the code (the server builds and reloads it) and runs a smoke test. A merge that changes only docs, specs, tests and repository tooling is skipped, and the workflow is live: its secrets and the migration baseline have been in place since 2026-10-03 (`deploy/README.md`, Automatic deploys). So before merging, check that every new migration is compatible with the code that is running while it is applied (dropping or renaming something in use takes two merges, the second after the first has deployed) and that the generated types are current (`npm run types:gen` from the local DB; CI's `types:check` fails when they are stale); the Supabase advisors (`get_advisors`) stay a manual look after a schema change, and regenerated trail seeds (spec 0004) are not applied by the workflow: apply them and clear the cache by hand (`deploy/README.md`, After the seeds change). The manual way, migrations through the Supabase MCP (`apply_migration`), then recording each applied file (`insert into public.applied_migrations (file_name) values ('0031_x.sql')`, otherwise the workflow applies it a second time) and then `git push production main`, is only for a rollback or when the workflow is broken (see Server & Deployment).

A tool call that the auto-mode classifier denies is not retried, split or routed around, and it is not a place to stop: say so in one line, carry on with every step that does not depend on it, and give the user the denied command (in its own `bash` block) in the final message. Run commands that delete or change shared state as their own call, never chained with reads, so a denial cannot swallow the rest.

### What the fresh review checks
The reviewer reads the task issue (`gh issue view`), the pull request description, the specs it lists and the diff like a stranger, runs `npm run check`, reads the E2E specs, and looks for:
- requirements of the task that do not hold, ACs not implemented as written or built twice, behaviour no AC describes, ACs without a test that really asserts them (weak assertions, mocks standing in for the thing under test);
- a migration in the diff that the code running in production could not live with while it is applied (a drop or rename of something the running code uses takes two merges, the second after the first has deployed: spec 0026 AC-5), one that is not named `NNNN_slug.sql` after the number of the task issue that adds it, or a schema change without regenerated types (`npm run types:gen`) (a merge deploys, so no one looks after the reviewer);
- the `manual` coverage rows of the touched areas: done where the reviewer can (it can run commands and read code), and named when they have no date or the change may have invalidated them;
- specs true in both directions, not only where the diff touches them (and no spec describing behaviour that is not built): ACs of the touched specs that the code does not satisfy, behaviour of the touched area that no AC states, a Goal or note that tells the story of a change instead of describing the area; spec hygiene: ACs renumbered or deleted instead of marked `Removed`, the owning spec not updated, the `specs/README.md` index, statuses and coverage not true, a pull request whose "Spec changes" section is empty or untrue;
- a user-visible change missing from the changelog, or described untruly; leftovers of anything renamed or moved (code, routes, message keys in every language, docs, specs);
- the gotchas below; regressions for signed-out visitors, other locales, 375 px screens and no-JS or not-yet-hydrated pages;
- security and privacy: who may call what (RLS, `auth.uid()`), secrets or personal data in logs, open redirects, anything new that is public.


## Where the rules live
Every area has a spec (index in `specs/README.md`); the work on them is in GitHub issues labelled `task` (`gh issue list --label task`); how the two work: 0034. Entry points: progress `src/lib/progress.ts` (0001); stamping `src/app/[locale]/dashboard/actions.ts` (0002); map and route planner `src/components/TrailMap.tsx`, `src/lib/route-*.ts` (0003); trail data `scripts/build-data.mjs`, never hand-edit its outputs (0004); the About page's text must stay true: no "open source"/"PWA" until they are (0015); fresh-context review before merge: 0022; feature flags (`src/lib/feature-flags.ts`, a database state read per request, no deploy to switch one, also from the Telegram bot through `src/app/api/telegram/route.ts`: 0035); friends, behind the `friends` flag, which is on in production (checked 2026-10-04: 0024).

## Gotchas
- `next.config.ts` wires next-intl by hand: `createNextIntlPlugin` loads native `@swc/core`, which fails on this Windows machine. Its `distDir` comes from `NEXT_DIST_DIR` (`.next-test` / `.next-e2e` for the test servers).
- `src/proxy.ts` matcher is a TS string: the extension escape must stay `\\.` (a single `\.` makes it match only `/`; `src/proxy.test.ts` guards this).
- Landing page and dashboard both check the session with `getUser()`; mixing in `getClaims()` can loop on a revoked but unexpired token.
- Server actions (stamp, delete-account, feedback, friends) never throw: they return a result (a thrown error reaches the client as an opaque message). Stamping writes with `ignoreDuplicates`; its optional `date` only dates rows that are *created*. Editing a date is a separate update-only action (`setStampDate`); never save a date on every `change` event (Chrome fires one per keystroke): see `StampDateInput`.
- Build redirect URLs in route handlers with `requestOrigin(request)` (`src/lib/origin.ts`; `originFromHeaders` in Server Components), never from `request.url` (it says `localhost` behind Caddy) or raw forwarded headers.
- The service role key (`SUPABASE_SERVICE_ROLE_KEY`, `src/lib/supabase/service.ts`) belongs to the Telegram webhook alone (spec 0035 AC-23): it bypasses row level security, so no page, action or component imports it, and it is never logged or prefixed `NEXT_PUBLIC_`. The test server blanks it.
- Failed actions log one line through `src/lib/log.ts` (`[stamp-action]`, `[friends]`, spec 0008), the place to hook in error monitoring; never log emails, ids, tokens, input or Supabase `details`/`hint`. The Telegram token is in the request URL, so never log URLs, fetch error objects or message text; the public feedback form is validated, honeypotted and rate limited (`npm run telegram:check`).
- A feature flag is read per request with `flagOn("key")` (`src/lib/feature-flags-server.ts`; spec 0035): a feature that is off answers 404 and its actions `disabled`, so check it in both. A new flag is declared in `FLAGS` and gets a row in a migration. E2E tests that switch a declared flag live in `e2e/feature-flags.spec.ts` (own Playwright project, flags are global).
- Tests that need the local Supabase (`tests/*-database.test.ts`, `friends-migration`, `database-rules`, `seed-cleanup`) call `requireDatabase(ctx, [tables])` from `e2e/local-db.ts`, never their own `ctx.skip()`: without a database they skip, but where `REQUIRE_LOCAL_DB` is set they fail. Only CI's "Database rule tests" step sets it (spec 0007 AC-12, AC-13); a new database test file is also added to that step.
- Node's `fetch` keeps sockets open and crashes a process at exit on Windows (libuv assertion): scripts throw instead of `process.exit()`, and E2E helpers use Playwright's `request`, not `fetch`.
- Full-height pages (landing, error) use `flex-1`, not `min-h-screen`: the footer must stay on the first screen.
- Sign-out and the dummy login are plain form POSTs to route handlers under `src/app/auth/` (work before hydration). The dummy login needs BOTH `TEST_LOGIN=1` and a localhost Supabase URL: keep both guards.
- Every user-visible string goes into every `messages/*.json` (`tests/messages.test.ts` checks parity). Message keys and `Locale` are typed (`src/i18n/global.ts`): a page that reads `params.locale` must narrow it with `hasLocale(routing.locales, locale)` / `notFound()` first.
- The root layout renders no `<html>` (locale layouts do), so `src/app/not-found.tsx` brings its own document; `src/app/[locale]/error.tsx` is the localized error boundary (Next 16 passes `retry`, not `reset`). The UI is light-only (`color-scheme: light`); don't add body colour overrides.
- `public/maplibre/` is generated by `scripts/copy-maplibre-worker.mjs` in the `pre*` npm scripts: always start Next through npm scripts, not bare `next`.
- E2E: never against `next dev` (each stamp re-renders the whole dashboard, 15-20 s under parallel tests). Each test signs in as a fresh user (`signInAsNewUser`); wait for hydration (`expandAllStages`) before clicking client-side buttons.
- Docker Desktop here crashes on start after a leftover Unix-socket file (Windows error 1920, "initializing Inference manager"): quit it, rename `%LOCALAPPDATA%\Docker\run` (and `%LOCALAPPDATA%\docker-secrets-engine` if named) aside, start again.
- Node comes from winget: in a fresh shell refresh PATH if `npm` isn't found.

## Server & Deployment
Production is a DigitalOcean droplet (`188.166.117.212`, 1 GB RAM + swap) running PM2 behind Caddy at `kektura-tracker.com`, database and sign-in on Supabase cloud. Everything about it (setup, environment variables, deploying, rolling back, logs) is in `deploy/README.md` (spec 0020); `deploy/post-receive` is the git hook (a copy lives on the server).
- Deploy: a merge to `main` deploys by itself (step 7; setup and secrets in `deploy/README.md`, Automatic deploys). The manual way, `git push production main` after applying the migrations (the hook never touches the database), is only for a rollback or when the workflow is broken: never push to `production` unless the user asks.
- The hook stops at the first failing step. Server-only values (`TELEGRAM_*`, `SITE_URL`, `SUPABASE_SERVICE_ROLE_KEY`) live in `~/kektura_app/.env.local` on the server and apply with `pm2 restart kektura --update-env`; `TEST_LOGIN` must never be set there.
