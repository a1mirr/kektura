# Kektura tracker

Web app for tracking progress on the Országos Kéktúra (Hungary's Blue Trail): users sign in with Google, mark stamping points (bélyegzőhelyek) and see statistics.

## Stack
- Next.js 16 (App Router, TypeScript, Tailwind 4). Read `node_modules/next/dist/docs/` before using unfamiliar APIs — this version differs from older ones (e.g. `middleware.ts` is now `src/proxy.ts`, route `params` are Promises).
- next-intl for i18n: locales `ru` (default), `en`, `hu`; messages in `messages/*.json`; routes under `src/app/[locale]`. Add every new string to all three files.
- Supabase: Google OAuth + Postgres with RLS. Schema in `supabase/migrations`, seed in `supabase/seed.sql`.
- Recharts for charts.
- Vitest (+ Testing Library/jsdom for components) for tests.

## Workflow: spec first, tests prove it
- Every feature, behaviour change or non-trivial bug fix starts with a spec in `specs/` (copy `specs/_template.md` to `specs/NNNN-slug.md`; numbered acceptance criteria `AC-n`). Show the spec to the user and settle open questions before implementing. See `specs/README.md`.
- Tests cite the spec: `describe("spec NNNN: …")`, `it("AC-n: …")`. Changing existing behaviour = edit the spec that owns it (never renumber ACs) + its tests, in the same change.
- Keep logic out of pages and big components: pure functions in `src/lib` (tested in Node), components get small `*.test.tsx` files with `// @vitest-environment jsdom`. Async Server Components can't be unit-tested; list their behaviour as `manual` in the spec's coverage table.
- A Stop hook (`.claude/settings.json` -> `.claude/hooks/stop-check.mjs`) runs typecheck + lint + tests before a turn ends whenever source files changed, and blocks until they pass; it also asks once when app code changed without any spec/test change. Don't work around it: fix the failure or explain why no spec/test change is needed.

## Notes
- `next.config.ts` wires next-intl by hand (no `createNextIntlPlugin`): the plugin loads native `@swc/core`, which fails its cache-permission check on this Windows machine. Don't switch back without testing `npm run build`.
- Trail data comes from the official MTSZ GPX files linked on https://www.kektura.hu/okt-szakaszok (`okt_bh_<date>.gpx` stamping points, `okt_teljes_bh_<date>.gpx` full route). `node scripts/build-data.mjs <stamps.gpx> <route.gpx>` regenerates `supabase/seed.sql` and `public/data/okt-route*.json` — don't edit those by hand. There are 220 rows (checkpoints) = 161 places, matching the official count: alternative stamps at one place (`_1`/`_2`/`_3` suffix) share a `place_key`, and stamping one stamps them all (`setPlacesStamped` works per `place_key`, also for a single place). `_B`/`_C` points are separate places. `km_from_start` is the snapped distance along the track; a place sits at the km of its furthest-along variant (variants can be up to ~3 km apart, and the MTSZ table lengths measure to that one), both in `src/lib/progress.ts` (`buildPlaces`) and in `build-data.mjs` (`placeKm`). Shared GPX/geometry helpers live in `scripts/lib/geo.mjs`. The generated seeds run in a transaction and delete rows the new source no longer has, moving users' stamps to the remaining variants of the same place first (spec 0004 AC-9). `tests/trail-data.test.ts` checks the generated files against each other and the MTSZ table: run `npm test` after regenerating.
- Stamp server actions (`src/app/[locale]/dashboard/actions.ts`: `setPlacesStamped`, `setExtraStamped`) never throw: they return an `ActionResult` (`src/lib/action-result.ts`) because a thrown error reaches the client as an opaque message. Writes go through `asUser`, which checks the session, catches everything and revalidates the dashboard on success. Client buttons go through `ActionButton` / `useStampAction` (an `unauthorized` result refreshes the page, which redirects to sign-in; `failed` shows `actionFailed`); the map popup does the same by hand. Writes use `ignoreDuplicates` so `user_extra_stamps`, which has no UPDATE policy, never hits ON CONFLICT DO UPDATE.
- `src/proxy.ts` refreshes the Supabase session (`getClaims`) before running the next-intl middleware and forwards the refreshed cookies to both the request and the response. The `matcher` is a TS string: the file-extension escape must be `\\.` (a single `\.` collapses to `.` and makes the matcher match only `/`).
- The root layout renders no `<html>` (each locale layout does), so `src/app/not-found.tsx` brings its own document; `src/app/[locale]/error.tsx` is the localized error boundary (Next 16 passes `retry`). The UI is light-only (`color-scheme: light` in `globals.css`; no body colour overrides, they would beat the Tailwind classes on `<body>`).
- Stage numbering: list labels are `<stage>.<n>` (27 official sections, `checkpoints.stage` + `stage_seq`; e.g. 1.1 Írott-kő … 27.7 Hollóháza). A stamp belongs to the stage it ends; Írott-kő (1.1) and Nagymaros (17.1, ferry gap after Visegrád) are the only stage starts that get a number. The mapping comes from `scripts/data/okt-stages.json`, extracted from MTSZ's section table PDF (`https://turistaterkepek.hu/kekturahu/tablazatok/okt_szakasz_adatok.pdf`); `build-data.mjs` reads it and fails loudly if a place name has no stage. Re-extract the JSON when MTSZ changes stages.
- Stamps list is grouped into collapsible stages (`StageSection`, open/closed state in localStorage; `StageControls` = expand/collapse all; rows stay in the DOM when collapsed and a map click opens the stage via `src/lib/stage-events.ts`). The per-stage button calls `setPlacesStamped`: marking adds the stage's own places plus its starting point (previous stage's last place, unless the stages don't join — Visegrád/Nagymaros) so the first stretch counts as walked; unmarking removes only the stage's own places.
- Map click on a stamp opens an action popup (route from here / route to here / mark or unmark walked / show in list). Choosing both route ends highlights the stretch (amber `segment` layer) and shows distance, ascent, descent and time in a panel under the map. Numbers come from `public/data/okt-hops.json` (160 hops between neighbouring places, built by `build-data.mjs` from the MTSZ table in `scripts/data/okt-stages.json`; the Visegrád→Nagymaros ferry hop has no times). Walking east→west swaps ascent/descent and uses the "back" times. Sums were checked against the table totals (1183.1 km, 31915/32500 m, 347:45).
- Extra (non-official) stamps: 72 rows in `extra_stamps` from heyjoe.hu's `okt_pecsetek.gpx` (`https://heyjoe.hu/pecset_gpx.php?mozgalom=okt`; everything >60 m from an official point). Pass it as 3rd arg to `scripts/build-data.mjs` to regenerate `supabase/seed_extra.sql`. Tracked in `user_extra_stamps`, never counted in the 161. No stamp artwork exists in any open source found (MTSZ owns it), so don't scrape for it — the idea is user-uploaded photos.
- Migrations (`0001`-`0006`) are applied to the Supabase project through the Supabase MCP connector (`apply_migration` / `execute_sql`); keep the files in `supabase/migrations` in sync with what is applied. After a schema change regenerate `src/lib/supabase/database.types.ts` (MCP `generate_typescript_types`); both Supabase clients are typed with it, so column typos fail `tsc`. RLS policies use `(select auth.uid())` and `to authenticated`; check `get_advisors` after DDL.
- Progress rule: stamps can be collected in any order; a stretch between two neighbouring places (trail order by `km_from_start`) counts as walked only if BOTH are stamped. `walkedRanges` in `src/lib/progress.ts` builds the km intervals (`doneRanges`); km/percent stats and the blue line on the map both derive from it. The dashboard page only fetches and renders: all rules live in `src/lib/progress.ts` (spec 0001).
- A signed-in visitor of `/` is redirected to the dashboard. Landing page and dashboard both use `getUser()` for that check: mixing it with `getClaims()` could loop on a revoked but unexpired token.
- Map (`src/components/TrailMap.tsx`; pure geometry in `src/lib/route-geometry.ts`, route-planner sums in `src/lib/route-stats.ts`, spec 0003) draws the route from `public/data/okt-route.json` (~30 m simplification) and swaps to `okt-route-detail.json` at zoom >= 9; walked stretches (`doneRanges`) are blue, the rest grey dashed. Below the map are layer toggles (walked stretches, official stamps, extra stamps, restaurants; choices persist in localStorage) and a fullscreen button (native Fullscreen API + CSS overlay fallback, Esc exits). Restaurants come from `public/data/restaurants.json` (only those within 5 km of the trail, built by `scripts/build-restaurants.mjs` from an etteremhet.hu results page). Clicking a dot scrolls to its list row (`place-<key>` / `extra-<id>` ids) and the 📍 button in a row flies the map to it (`src/lib/map-focus.ts`).
- `public/maplibre/` is generated (gitignored, ESLint-ignored): `predev`/`prebuild` run `scripts/copy-maplibre-worker.mjs`, so start the app via `npm run dev` / `npm run build`, not bare `next`.
- Node is installed via winget; in a fresh shell refresh PATH if `npm` isn't found.

## Commands
- `npm run dev` — dev server
- `npm run build` — production build (needs `NEXT_PUBLIC_SUPABASE_*` env vars, see `.env.example`)
- `npm test` — all tests once (`npm run test:watch` while working); `npm run check` — typecheck + lint + tests, the same gate the Stop hook runs
