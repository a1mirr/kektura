# Kektura tracker

Tracks progress on the Országos Kéktúra (Hungary's Blue Trail): Google sign-in, mark the 161 official stamping places (plus extra stamps), see walked km, stages, a map and a route planner.

Stack: Next.js 16 (App Router, TS, Tailwind 4), next-intl (`ru` default, `en`, `hu`), Supabase (Google OAuth, Postgres + RLS), MapLibre, Recharts, Vitest + Testing Library, Playwright. Next 16 differs from older versions (`src/proxy.ts` instead of middleware, `params` are Promises): read `node_modules/next/dist/docs/` before using an unfamiliar API.

## Commands
- `npm run dev` (port 3000, production Supabase via `.env.local`); `npm run build`
- `npm test` / `npm run test:watch`; `npm run check` = typecheck + lint + tests (the Stop hook's gate)
- Test server: `npm run testdb:start` | `testdb:reset` | `testdb:stop` (local Supabase in Docker), `npm run dev:test` (port 3001, dummy login)
- `npm run e2e`: Playwright against a production build of the test server on port 3002

## Workflow
A change goes through these steps in order. CI (`.github/workflows/ci.yml`) runs the same checks plus E2E on every push; `backup.yml` dumps user data weekly.

1. **Spec first.** Every feature, behaviour change or non-trivial fix starts as `specs/NNNN-slug.md` (from `specs/_template.md`) with numbered acceptance criteria; settle open questions with the user before coding. Specs are always written in English. Tests cite them: `describe("spec NNNN: …")`, `it("AC-n: …")`. Changing behaviour = edit the owning spec (never renumber ACs) + its tests in the same change. Details: `specs/README.md`.
2. **Build.** Logic in `src/lib` as pure functions with unit tests; pages only fetch and render. Components get `*.test.tsx` with `// @vitest-environment jsdom`. Async Server Components can't be unit-tested: cover them with E2E. The **Stop hook** (`.claude/hooks/stop-check.mjs`) blocks the end of a turn until typecheck + lint + unit tests are green, and asks once when app code changed without a spec/test change: fix the failure, don't work around it. Run `npm run e2e` yourself before committing user-flow changes (needs Docker, so the hook doesn't).
3. **Migrations go local first.** New file in `supabase/migrations`, named `NNNN_slug.sql` after the number of the spec that owns it (`0024_friends.sql`; the older 0001-0008 predate this). The CLI takes the digits as the version, which must be unique, so a spec owns one migration file: edit it until it is applied to production, then a later schema change needs its own spec number. It must not depend on a higher-numbered migration (production applies in merge order, a fresh reset by number) → `npm run testdb:reset` → tests + E2E. RLS policies use `(select auth.uid())` and `to authenticated`.
4. **Changelog** (spec 0018 AC-7). A change users can see (behaviour, a rename, a page) adds or extends an entry in `src/content/changelog.ts` in the same pull request, in all three languages; process, test, refactor and deploy-file changes add none. Dates can't repeat, so a change made on the newest entry's date joins that entry.
5. **Branch and pull request.** `main` is GitHub's default branch and the one that gets deployed. Work on a topic branch (`git switch -c <topic>`), push it and open the pull request yourself with `gh pr create --base main --head <topic> --title "<title>" --body-file <file>`. `gh` is installed (per user, in %LOCALAPPDATA%\Programs\gh\bin on the user's PATH, signed in as `a1mirr`; a terminal opened before the install needs a restart). A shell without a terminal can't answer gh's prompts, so title and body are always given; start the body file from a copy of `.github/pull_request_template.md` (gh doesn't apply it to `--body-file`) and fill in its checklist and review findings. Follow CI with `gh pr checks <n> --watch`. Spec 0021 owns these pull request rules and the hook. Never push to `main` on GitHub: a `pre-push` hook (`.githooks/`, spec 0021) refuses it. Install it once per clone with `npm run hooks:install`; pushing to the `production` remote is unaffected. If another Claude session shares the checkout, use your own `git worktree add .claude/worktrees/<name> -b <topic> main` (junction `node_modules`) and leave its uncommitted files alone.
6. **Fresh-context review before merge** (spec 0022). When the change is done and committed (spec closed, `npm run check` green, E2E run for user-flow changes) and before it is merged, an agent with no context of the work reviews it: spawn the `fresh-reviewer` agent (`.claude/agents/fresh-reviewer.md`) and tell it only the spec number (`none` for a small change that has no spec) and the base branch (`origin/main`, after `git fetch origin`: a local `main` can be stale), never your reasoning or what to look at. Fix every valid finding and answer the rest in the pull request description, with the commit that was reviewed. Fixes that change code, tests or behaviour get another fresh review (a review of an earlier state doesn't count); wording-only fixes don't, so the pull request's head is the reviewed commit plus, at most, wording fixes. Never hand a pull request over as ready to merge without it, and leave the working tree alone while the review runs. Every change a person or Claude writes is reviewed, documentation included; Dependabot's pull requests are not (CI judges them). In the session that edited the agent file, spawn a general-purpose agent with the file's body as the brief (agents load at session start).
7. **Merge, migrate, deploy.** Merge with `gh pr merge <n> --merge --match-head-commit <full-sha>` (the repo uses merge commits; the full 40-character sha of the pull request's current head, `git rev-parse HEAD` after the last push: the reviewed commit plus, at most, wording fixes; a draft needs `gh pr ready`) on the owner's standing permission (given in chat on 2026-10-03, revocable) for pull requests you wrote, once CI is green and the fresh-context review is done (CI's jobs: "Typecheck, lint, unit tests" and "End-to-end tests"); never `--admin`. Delete the pull request's branch after the merge, remote and local: `git fetch origin`, check it is in `main` (`git merge-base --is-ancestor origin/<topic> origin/main`), retarget any open pull request that is based on it (`gh pr edit <m> --base main`), `git push origin --delete <topic>`, then `git branch -d <topic>` from a checkout whose HEAD contains the merge (in your own worktree: `git switch --detach origin/main` first; never `-D`). Delete only branches of pull requests you merged, or that the user asked you to clean up: if another session has the branch checked out, leave the local branch and tell the user. The merge itself deploys (spec 0026, `.github/workflows/deploy.yml`): once CI is green on `main` it applies the missing migrations to production, pushes the code (the server builds and reloads it) and runs a smoke test. A merge that changes only docs, specs, tests and repository tooling is skipped, and the workflow does nothing until the repository secrets exist (`deploy/README.md`, Automatic deploys). So before merging, check that every new migration is compatible with the code that is running while it is applied (dropping or renaming something in use takes two merges, the second after the first has deployed) and that the generated types are current (`npm run types:gen` from the local DB; CI's `types:check` fails when they are stale); the Supabase advisors (`get_advisors`) stay a manual look after a schema change. The manual way, migrations through the Supabase MCP (`apply_migration`) and then `git push production main`, is only for a rollback or when the workflow is broken (see Server & Deployment).

### What the fresh review checks
The reviewer reads the spec and the diff like a stranger, runs `npm run check`, reads the E2E specs, and looks for:
- ACs not implemented as written or built twice, behaviour no AC describes, ACs without a test that really asserts them (weak assertions, mocks standing in for the thing under test);
- spec hygiene: ACs renumbered or deleted instead of marked `Removed`, the owning spec not updated, the `specs/README.md` index, status and coverage not true;
- a user-visible change missing from the changelog, or described untruly; leftovers of anything renamed or moved (code, routes, message keys in all three languages, docs, specs);
- the gotchas below; regressions for signed-out visitors, other locales, 375 px screens and no-JS or not-yet-hydrated pages;
- security and privacy: who may call what (RLS, `auth.uid()`), secrets or personal data in logs, open redirects, anything new that is public.


## Where the rules live
Every area has a spec: index in `specs/README.md`. Entry points: progress `src/lib/progress.ts` (0001); stamping `src/app/[locale]/dashboard/actions.ts` (0002); map and route planner `src/components/TrailMap.tsx`, `src/lib/route-*.ts` (0003); trail data `scripts/build-data.mjs`, never hand-edit its outputs (0004); the About page's text must stay true: no "open source"/"PWA" until they are (0015); fresh-context review before merge: 0022; friends, behind `FF_FRIENDS=1` and off in production until switched on (0024).

## Gotchas
- `next.config.ts` wires next-intl by hand: `createNextIntlPlugin` loads native `@swc/core`, which fails on this Windows machine. Its `distDir` comes from `NEXT_DIST_DIR` (`.next-test` / `.next-e2e` for the test servers).
- `src/proxy.ts` matcher is a TS string: the extension escape must stay `\\.` (a single `\.` makes it match only `/`; `src/proxy.test.ts` guards this).
- Landing page and dashboard both check the session with `getUser()`; mixing in `getClaims()` can loop on a revoked but unexpired token.
- Server actions (stamp, delete-account, feedback, friends) never throw: they return a result (a thrown error reaches the client as an opaque message). Stamping writes with `ignoreDuplicates`; its optional `date` only dates rows that are *created*. Editing a date is a separate update-only action (`setStampDate`); never save a date on every `change` event (Chrome fires one per keystroke): see `StampDateInput`.
- Build redirect URLs in route handlers with `requestOrigin(request)` (`src/lib/origin.ts`; `originFromHeaders` in Server Components), never from `request.url` (it says `localhost` behind Caddy) or raw forwarded headers.
- Failed actions log one line through `src/lib/log.ts` (`[stamp-action]`, `[friends]`, spec 0008), the place to hook in error monitoring; never log emails, ids, tokens, input or Supabase `details`/`hint`. The Telegram token is in the request URL, so never log URLs, fetch error objects or message text; the public feedback form is validated, honeypotted and rate limited (`npm run telegram:check`).
- A page that reads a runtime flag (`FF_FRIENDS`) must opt out of static rendering (`connection()`, `src/lib/friends-flag.ts`), or the build's value sticks.
- Node's `fetch` keeps sockets open and crashes a process at exit on Windows (libuv assertion): scripts throw instead of `process.exit()`, and E2E helpers use Playwright's `request`, not `fetch`.
- Full-height pages (landing, error) use `flex-1`, not `min-h-screen`: the footer must stay on the first screen.
- Sign-out and the dummy login are plain form POSTs to route handlers under `src/app/auth/` (work before hydration). The dummy login needs BOTH `TEST_LOGIN=1` and a localhost Supabase URL: keep both guards.
- Every user-visible string goes into all three `messages/*.json` (`tests/messages.test.ts` checks parity). Message keys and `Locale` are typed (`src/i18n/global.ts`): a page that reads `params.locale` must narrow it with `hasLocale(routing.locales, locale)` / `notFound()` first.
- The root layout renders no `<html>` (locale layouts do), so `src/app/not-found.tsx` brings its own document; `src/app/[locale]/error.tsx` is the localized error boundary (Next 16 passes `retry`, not `reset`). The UI is light-only (`color-scheme: light`); don't add body colour overrides.
- `public/maplibre/` is generated by `scripts/copy-maplibre-worker.mjs` in the `pre*` npm scripts: always start Next through npm scripts, not bare `next`.
- E2E: never against `next dev` (each stamp re-renders the whole dashboard, 15-20 s under parallel tests). Each test signs in as a fresh user (`signInAsNewUser`); wait for hydration (`expandAllStages`) before clicking client-side buttons.
- Docker Desktop here crashes on start after a leftover Unix-socket file (Windows error 1920, "initializing Inference manager"): quit it, rename `%LOCALAPPDATA%\Docker\run` (and `%LOCALAPPDATA%\docker-secrets-engine` if named) aside, start again.
- Node comes from winget: in a fresh shell refresh PATH if `npm` isn't found.

## Server & Deployment
Production is a DigitalOcean droplet (`188.166.117.212`, 1 GB RAM + swap) running PM2 behind Caddy at `kektura-tracker.com`, database and sign-in on Supabase cloud. Everything about it (setup, environment variables, deploying, rolling back, logs) is in `deploy/README.md` (spec 0020); `deploy/post-receive` is the git hook (a copy lives on the server).
- Deploy: a merge to `main` deploys by itself (step 7; setup and secrets in `deploy/README.md`, Automatic deploys). The manual way, `git push production main` after applying the migrations (the hook never touches the database), is only for a rollback or when the workflow is broken: never push to `production` unless the user asks.
- The hook stops at the first failing step. Server-only values (`TELEGRAM_*`, `SITE_URL`, `FF_FRIENDS`) live in `~/kektura_app/.env.local` on the server and apply with `pm2 restart kektura --update-env`; `TEST_LOGIN` must never be set there.
